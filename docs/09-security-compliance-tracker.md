# Security & Compliance Tracker

Living record of every security and legal-compliance finding surfaced during development — not just chat history. Updated whenever new work turns up something worth tracking. Severity is roughly: **Critical** (actively exploitable, high impact) → **High** (real risk, narrower blast radius or needs specific conditions) → **Medium** → **Low**.

## Fixed

| # | Severity | Area | Finding | Fixed |
|---|----------|------|---------|-------|
| 7 | Critical | Security | Every JWT signing/verification call used `process.env.JWT_SECRET ?? "jwt_secret"` — a hardcoded fallback secret sitting in source. If the env var was ever unset, tokens became forgeable with a publicly-known string. Fixed: centralized `JWT_SECRET` config that throws at startup if unset (fail loud, not fail open). | Backend security pass |
| 8 | Critical | Security | The `/api/auth/resubmit` endpoint used `jwt.decode()` instead of `jwt.verify()` — the token's signature was **never actually checked**, meaning anyone could forge a token with an arbitrary student `id` claim and overwrite a different student's ID-verification document, regardless of how strong `JWT_SECRET` was. Fixed to use `jwt.verify()`. | Backend security pass |
| 9 | High | Security | Outdated `axios` and transitive dependencies carried ~20 known CVEs (SSRF, prototype pollution, credential leakage, ReDoS). Fixed via `npm audit fix` (non-breaking). | Backend security pass |
| 10 | Medium | Security | CORS was fully open (`cors()` with no options — any origin allowed). Restricted to known production domains + local dev + Vercel preview URLs. | Backend security pass |
| 11 | Low-Medium | Security | No security headers (`X-Content-Type-Options`, `X-Frame-Options`, HSTS, etc.). Added `helmet` with default config. | Backend security pass |
| 12 | Medium | Security | Vercel's serverless functions don't share memory between invocations, and without `app.set("trust proxy", 1)`, `req.ip` would've resolved to Vercel's proxy for every request — collapsing any IP-based rate limiting into one shared bucket for the whole site. Caught before shipping rate limiting. | Rate limiting rollout |
| 13 | Medium | Security | No rate limiting existed anywhere — a public API with a Stripe-charging endpoint had no abuse protection. Added tiered rate limiting (Upstash Redis): strict on auth, moderate on bid/payment/cancel, light general floor. | Rate limiting rollout |
| 14 | — | CI/CD | No automated build check before merge — every change went to production off a manually-run local build. Added GitHub Actions CI (build gate, not a test gate — no test suite exists yet) + branch protection requiring it to pass, `enforce_admins: true`. | CI rollout |
| 15 | High | CA/US legal | Cookie consent banner's "Dismiss" button called the identical handler as "Accept" — there was no way to actually decline tracking. This is the specific "asymmetric choice" dark pattern CPRA regs (11 CCR §7004) prohibit, and directly contradicted the Privacy Policy's promise of working "in-product cookie controls." Fixed: real, equally-weighted Reject button, verified via network trace to actually block GA/Clarity/Meta Pixel. | Cookie consent fix |
| 16 | Medium | CA/US legal | Privacy Policy claimed to honor Global Privacy Control (GPC) signals, but the code never read `navigator.globalPrivacyControl`. Implemented. | Cookie consent fix |
| 17 | Medium | CA/US legal | No persistent way to change a cookie choice after the initial banner — CPRA requires an accessible, ongoing opt-out mechanism, not just a one-time popup. Added a "Cookie Settings" link in the footer that reopens the banner from any page. | Footer link fix |
| 18 | Medium | Legal (ToS) | ToS Section 6.1 stated all bookings were "final, non-cancellable, non-refundable" with no exceptions, and Section 4.3 independently repeated the same absolute claim — both directly contradicted the newly-built admin cancellation/refund feature, and arguably meant the site was already out of compliance with CA SB 644's mandatory 24-hour cancellation window (in effect since July 2024) regardless of whether a cancel feature existed. Rewrote both sections to describe the real policy. | Bid cancellation feature |
| 19 | Medium | Legal (checkout) | The final-bid confirmation screen was missing two disclosures the ToS itself already promised (Section 6.0): merchant-of-record identity + card statement descriptor, and explicit charge-timing. Also added the ToS's already-established 2-guest-per-room occupancy and accessibility disclosures (Section 8.4), shown the way HotelTonight surfaces the same policy at checkout. | Lock-in modal disclosures |
| 20 | — | Legal (Cloudbeds) | Deadline never masked guest contact info the way some OTAs do (per Privacy Policy 5.2.1) but the Cloudbeds booking export omitted phone number. Added. | Cloudbeds phone field |
| 21 | High | Security | `nodemailer` v7 carried 6 CVEs (SMTP/CRLF command injection via `envelope.size`, transport `name` option, and `List-*` headers; `jsonTransport` bypassing file/URL access restrictions; TLS cert validation skipped during OAuth2 token fetch; the `raw` message option bypassing file/URL restrictions enabling SSRF). Checked `sendEmail.ts`'s actual usage before upgrading: it only calls `createTransport({host, port, secure, auth: {user, pass}})` and `sendMail({from, to, subject, html[, text, replyTo]})` — no `envelope`, no custom transport `name`, no `List-*` headers, no `jsonTransport`, no OAuth2, no `raw` option. None of the 6 vulnerable code paths are reachable by this app regardless of what's in `to`/`subject`/`html`. Verified API compatibility in an isolated sandbox test (v9.0.3 + `jsonTransport` to exercise `createTransport`/`sendMail`/callback without needing real SMTP creds), then upgraded for real and confirmed a clean `npm audit` (0 vulnerabilities) and a passing `tsc` build. | Nodemailer v9 upgrade (PR #75) |
| 22 | High | Security | The `student-id-cards` Supabase Storage bucket had an `anon` INSERT policy — anyone on the internet could upload directly with no auth and no rate limit, bypassing the backend (and its rate limiting) entirely. Fixed: new `POST /api/auth/upload-url` endpoint (rate limited at the same 5-per-5-min tier as signup/resubmit) mints a short-lived, single-use Supabase signed-upload token via `createSignedUploadUrl()`; the resubmit context additionally requires a valid JWT (`jwt.verify`) scoping the upload path to the actual student. Migration `033_remove_anon_upload_student_id_cards.sql` drops the `anon` INSERT policy — the signed token is now the sole authorization, independent of that policy. `SignupPage.tsx` and `ResubmitPage.tsx` (the two pre-auth upload call sites) updated to request a signed URL before uploading; the three authenticated call sites (student profile, hotel place form, admin place form) were already covered by the separate `authenticated` INSERT policy and are unaffected. | Anon storage upload fix |

## Explicitly deferred (documented, not being fixed right now)

- **Per-day inventory / Cloudbeds allocation tracking** — `ARIUpdate` from Cloudbeds is accepted but not stored or enforced against bids yet. Real gap, scoped as its own future project (see conversation — proposed `PlaceDailyInventory` schema).
- **Guest count not collected at bid time** — affects the Cloudbeds booking export (`OrderAdults` hardcoded to 1) and the checkout disclosure screen (can't show "number of guests" as ToS 6.0 technically promises). Tied to the occupancy-per-room policy, not urgent given rooms are capped at 2 guests by policy either way.
- **Full WCAG/ADA audit** — not attempted; the existing accessibility statement is honestly worded (doesn't overclaim certification) and backed by real implemented features. Re-run `frontend/docs/accessibility-testing.md`'s manual checklist after future UI changes to bid/payment flows or modals, per its own "regression triggers" section.
